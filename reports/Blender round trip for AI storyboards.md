# Fingerprint what each shot camera sees

**Prompt-to-Scene Creator should keep the architecture its Blender bridge already ships but replace how it decides what changed.** Keep the native .blend built by a generated `bpy` script or a server-side `bpy` 5.2.3 subprocess, one Blender scene per shot plus an EDIT scene holding the cut, app-owned IDs in custom properties, and an exact JSON sidecar as the return path; the sidecar is right because every standard interchange format drops something a shot depends on (glTF turns a 35 mm lens into 55.695 mm and loses shift, depth of field and area lights, USD renames merged objects and turns keyframes into cache constraints, FBX and Alembic mangle or drop custom properties, and COLLADA is gone from 5.x). Target **Blender 5.2 LTS**, which runs Python 3.13 like the app, and **4.5 LTS**, which opens 5.2 files; 4.2 LTS received its last build in July 2026 and cannot read 5.x files. The weak point is detection. Run in real Blender 5.2.3 for this report, the current bridge reported **nine of ten common hand edits as "unchanged"** and would have silently discarded them: a dolly on a parent rig, an easing change, sensor fit, lens shift, depth of field, key-light energy, world colour, an animated walk and a trim in the EDIT timeline. A forced rebuild also duplicated every shot scene, and a later in-app edit reverted a hand-built camera arc to the template move. The fix is to define a shot's state as what its camera sees: sample every frame of the evaluated camera (all intrinsics) and of every visible object, read the timeline back, mint persistent IDs, merge field by field, and map each change to the smallest regeneration. For generation, no hosted model found (Seedance 2.0, Veo 3.1, Kling 3.0) accepts 3D or depth as geometry, so the edited previs should feed a keyframe-first pipeline of structure passes, a composition-preserving photoreal still and then image-to-video, using the greybox or depth video only as a role-labelled camera reference or as dense control on open models (Wan VACE, LTX-2), never as an appearance reference. Sora 2's inputs were not researched and remain the main open question.

## Every interchange format drops something a shot depends on

The format, version and API findings in this report come from round-tripping a test scene through Blender's official PyPI builds (`bpy` 5.2.3, 4.5.15 and 4.2.23) and from reading the add-on source shipped inside them; Blender's documentation sites were unreachable during the research. The evaluation of the shipped bridge in the next section comes from running its current code (commit `c25ece4`) in `bpy` 5.2.3 for this report. Hosted-model findings rest partly on third-party guides and are flagged where they do.

The test scene had a keyed camera (35 mm, shift, depth of field, zoom), proxy meshes, four light types and custom properties at several levels. It was exported and then re-imported into an empty scene in the same Blender version. No format came back whole ([bpy 5.2.3](https://pypi.org/project/bpy/5.2.3/), [bpy 4.2.23](https://pypi.org/project/bpy/4.2.23/)):

| Format | Survives a Blender round trip | Lost or altered | Role in the bridge |
|---|---|---|---|
| Native .blend (from a build script or `bpy`) | Everything, including custom properties on objects, object data, collections, scenes and strips | A 5.x file cannot be opened by 4.2 | The editable master |
| glTF 2.0 | Names; custom properties including nested dicts (as `extras`); scene properties; sampled transform keys | Lens refit from FOV onto a 36×24 sensor (**35 mm → 55.695 mm** at 2.39:1); render aspect; shift; depth of field; **area lights**; imported lens animation left inactive on the NLA | Viewing and web hand-off |
| USD | Lens, sensor, shift, depth of field, all four light types, scalar custom properties (`userProperties:*`), frame range | **Merged objects renamed after their data prims** (`CAM_shot_010` → `CAMDATA_shot_010`); dict properties silently omitted; scene and collection properties not written; keyframes become **Transform Cache constraints** on import; animation export off by default | Camera hand-off to other DCCs; server-side parsing |
| FBX | Names, transform keys, lens and focus keys, shift, depth of field | Dict properties stringified; area lights become point lights; white lights return 0.8 grey; custom-property export off by default | Avoid for metadata |
| Alembic | Names, cached animation | All custom properties; lights become Empties | Avoid |
| COLLADA | — | Operators removed in 5.x | Do not use |

The matrix vindicates the shipped bridge's central choice. Edits come back as `p2s-previs` JSON written by code running inside Blender, which reads evaluated values directly and never passes through an exporter's conversions ([BLENDER.md](/home/user/prompt-to-scene-creator/docs/BLENDER.md)). glTF earns a place only as a deliverable for viewers and web tools, and any re-import needs three fixups. First, set the render resolution from `aspectRatio`. Second, set `sensor_fit='HORIZONTAL'` and lens = 18/(A·tan(yfov/2)) instead of trusting the importer. Third, make the NLA lens action active. Set the scene fps before importing, too: the importer multiplies glTF seconds by the *current* scene's fps, so a 24 fps file imported into a 25 fps scene put its keys at frames 1.0417 to 50.0 ([glTF-Blender-IO](https://github.com/KhronosGroup/glTF-Blender-IO)). The bridge's own `.glb` uses the exporter's default `ACTIONS` mode without the experimental `export_pointer_animation`, so zooms never reach it. That is acceptable only while the docs keep calling it viewing-only.

USD is the better second channel for studios that continue in Houdini, Unreal or Maya, because it keeps every camera intrinsic. To use it, set `export_animation=True` (it is off by default), keep custom properties scalar with any structure encoded as JSON strings, and duplicate `p2s_id` onto camera and light data, because importers merge or split objects and their data. On return, sample the stage on the server with `usd-core` 26.11 rather than re-importing it into Blender. In testing, `usd-core` read every `userProperties:*` attribute and per-frame camera values from Blender's file, and it has shipped cp313 wheels since 25.8 ([usd-core 26.11](https://pypi.org/project/usd-core/26.11/), [usd-core history](https://pypi.org/project/usd-core/#history)). Collection Exporters, present in both 4.2 and 5.2, add one-click per-shot GLB or USD exports whose settings persist inside the .blend (`collection.exporter_add(name='IO_FH_usd')`) ([bpy 5.2.3](https://pypi.org/project/bpy/5.2.3/)).

### Blender 5.2 and 4.5 LTS are the support window

As of 5 November 2026 the current release is **Blender 5.2.3 LTS on Python 3.13**. That is also the app's interpreter, so `pip install bpy==5.2.3` gives the server a headless Blender without a second Python ([bpy on PyPI](https://pypi.org/project/bpy/), [bpy release history](https://pypi.org/project/bpy/#history)):

| Line | Python | Status on 5 Nov 2026 | Opens a 5.2 .blend? | Role for the app |
|---|---|---|---|---|
| 5.2.3 LTS | 3.13 | Current (PyPI upload 2026-10-22) | Yes | Primary target, server runtime, CI |
| 4.5.15 LTS | 3.11 | Still patched (PyPI upload 2026-10-22) | Yes, with warnings such as "negative users in strip" | Supported client, CI |
| 4.2.23 LTS | 3.11 | Last build uploaded 2026-07-21 | No ("not a blend file") | Build script only, or drop |
| 5.3 | — | No stable PyPI build seen; release status unconfirmed | — | Track through `fake-bpy-module-latest` |

The bridge docs now correctly say a server-built .blend needs 4.5 or newer. They still promise that the build script runs in "any Blender 4.2+", which commits the project to a line that no longer receives fixes ([BLENDER.md](/home/user/prompt-to-scene-creator/docs/BLENDER.md)). Make 4.5 the floor and run CI against both the 4.5.15 and 5.2.3 wheels. Tests run against `fake-bpy-module-latest` stubs, which are built from Blender's main branch, then give early warning of 6.0 removals ([fake-bpy-module-latest](https://pypi.org/project/fake-bpy-module-latest/)).

Four API changes between 4.2 and 5.2 decide whether generated code survives into 6.0. First, the VSE was renamed in stages. `strips` arrived beside `sequences` in 4.4, `new_effect` keywords changed in 4.5 and again in 5.0, `sequences` was removed in 5.0, handle properties arrived in 5.1, and 5.2 deprecates `frame_final_*` for removal in 6.0. Second, `Action.fcurves` is gone in 5.0, replaced by slotted channel bags. Third, ID names grew from 63 bytes (4.2 and 4.5) to 255 (5.2). Fourth, 5.2 compresses .blend files with zstd by default, so any tool that parses .blend files must handle magic bytes `28 B5 2F FD` ([bpy 5.2.3](https://pypi.org/project/bpy/5.2.3/), [fake-bpy-module-5.0](https://pypi.org/project/fake-bpy-module-5.0/), [fake-bpy-module-5.1](https://pypi.org/project/fake-bpy-module-5.1/)). The API surface to build on is:

| Job | Use (5.2 LTS, and 4.5 where noted) | Avoid or shim |
|---|---|---|
| Camera intrinsics | `sensor_fit='HORIZONTAL'`, `sensor_width=36`, explicit `shift_x/y` and `dof.*` | Defaults; treating `Camera.angle_y` as the vertical FOV (it is sensor-height based: 37.85° against a true 24.32° for 35 mm at 2.39:1) |
| Animation | `keyframe_insert`; `bpy_extras.anim_utils.action_get_channelbag_for_slot(action, anim.action_slot)` | `Action.fcurves` (removed in 5.0) |
| Evaluated state | `bpy.context.temp_override(scene=…)` with `evaluated_depsgraph_get()`; `world_to_camera_view`; `Camera.view_frame(scene=)` | `matrix_world` of a non-visible scene right after load, which reads as identity ([blender_addon.py](/home/user/prompt-to-scene-creator/prompt2scene/blender/blender_addon.py)) |
| Timeline | `sequence_editor.strips.new_scene/new_movie/new_image`; `Strip.left_handle/right_handle/duration` (5.1+); `TimelineMarker.camera`; `SceneStrip.scene_camera` | `sequences` (removed in 5.0); `frame_final_*` (deprecated in 5.2); `new_effect(seq1=…)` |
| Hooks | `bpy.app.handlers.save_pre/save_post/load_post/depsgraph_update_post` | Text-block `use_module` auto-run (off by default) |
| Files | Absolute paths into `bpy`, then `save_as_mainfile(relative_remap=True)`; `Collection.exporters` | Relative OS paths, which resolve against "/" in an unsaved session |
| Packaging | Extension with `blender_manifest.toml` and declared `permissions` | Legacy single-file `bl_info` add-on (support in 5.x unverified) |

Packaging needs the most immediate attention. The bridge ships as a legacy single-file add-on and also embeds itself in the .blend as a Text block with `use_module`. Blender's `use_scripts_auto_execute` preference defaults to off, though, and the 5.2.3 run for this report logged exactly that ("scripts disabled … skipping 'p2s_bridge.py'"). A user who simply opens the file sees no panel ([blender_addon.py](/home/user/prompt-to-scene-creator/prompt2scene/blender/blender_addon.py), [bpy 5.2.3](https://pypi.org/project/bpy/5.2.3/)).

The 4.2+ Extensions platform is the right container. Its `blender_manifest.toml` requires `id`, `schema_version`, `name`, `tagline`, `version`, `type = "add-on"`, `maintainer`, `license` and `blender_version_min`. The bridge would add `permissions` for `network` (sending edits to the app) and `files` (writing the sidecar), each with a one-line reason. Blender's own `blender_ext.py` validates and builds that zip under plain Python 3.13 without Blender, so the server can produce one per project ([Blender source](https://projects.blender.org/blender/blender)).

The server runtime is heavy. The Linux wheel is 402.8 MB and installs to 875 MB. It also links system X11 and GL libraries, there is no Linux aarch64 build for any version, and 5.0+ has no macOS x86_64 wheel. The bridge is right to run it in a subprocess with a timeout ([bpy files](https://pypi.org/project/bpy/5.2.3/#files)). Keep script auto-execution off whenever the server opens an uploaded .blend, which is untrusted input. Two questions stay open. One is whether an add-on that imports `bpy`, or a service that runs it, inherits GPL obligations: PyPI lists GPL-3.0, and Blender's license FAQ was unreachable. The other is how headless rendering behaves in the wheel, which was not tested.

## Nine of ten hand edits came back as unchanged

The shipped design gets the hard parts right. It follows the research's recommended structure of one scene per shot plus an EDIT scene, and it fixes the sensor at 36 mm horizontal so that a prompt's "35mm" means the same thing in Blender. It builds camera rotations from matrices, which sidesteps a trap the research measured (a naive XYZ Euler with roll is not a pure roll), and it compares rotations as matrices, so π against −π is not an edit. It evaluates each shot scene's own depsgraph, reads F-curves through the slot-filtered channel bag so object-data curves are not picked up by accident, and mutes handheld noise while sampling the underlying path. Untouched shots stay byte-identical, every applied import is snapshotted for rollback, and a shot the app changed after export is never overwritten ([BLENDER.md](/home/user/prompt-to-scene-creator/docs/BLENDER.md), [sync.py](/home/user/prompt-to-scene-creator/prompt2scene/blender/sync.py), [geometry.py](/home/user/prompt-to-scene-creator/prompt2scene/blender/geometry.py)).

Higgsfield's Blender connector is the closest commercial analogue ("prompt the blockout … adjust anything by hand, reblock"). It stresses the same idempotent-manifest and never-silently-change rules. Nothing found shows it detecting per-shot changes or regenerating only dirty shots, which is exactly the gap this bridge targets ([Higgsfield on X](https://x.com/higgsfield/status/2092255768770920506), [HF skill: blender-scene-spec](https://higgsfield.ai/plugins/blender)).

The detector was tested against the edits artists actually make. The demo project's 15 shots were built with the current bridge in `bpy` 5.2.3, and one hand edit was applied per shot. The file was then read back with the bridge's own `collect_edits()`, and the app's `import_edits()` gave the verdicts. Ground truth was measured inside Blender with `world_to_camera_view` and `Camera.view_frame`. Frame coordinates below use the app's convention, (0, 0) top-left ([local test script](/tmp/claude-0/-home-user-Speaker-Diarization/e6d7b62f-0368-5f51-9db4-b4ef76e4f814/scratchpad/eval_bridge/experiments.py), [bpy 5.2.3](https://pypi.org/project/bpy/5.2.3/)).

| Shot | Hand edit in Blender | What the camera now shows | Bridge verdict | Why it was missed |
|---|---|---|---|---|
| 2.1 | Camera moved 0.5 m sideways (positive control) | Reframed | **updated** | — |
| 3.2 | Camera parented to a dolly rig (an Empty) travelling 0.69 m | Lead's head drifts from (0.34, 0.37) to (0.23, 0.28) | unchanged | Sample frames come only from F-curves on the camera itself |
| 1.3 | Easing switched to constant, keys untouched | Camera sits 0.19 m from its old mid-shot position | unchanged | Sampled only at keyframes |
| 5.1 | Sensor fit switched to vertical | 24 mm becomes a **20.25 mm** full-frame equivalent | unchanged | Lens conversion assumes a horizontal fit (`lens_scale = 1.0` for VERTICAL) |
| 3.1 | Lens `shift_y` 0.1 | Lead's head moves from y 0.45 to 0.63 | unchanged | Shift is not in the schema |
| 4.2 | f/2.8 → f/16 | Shallow focus becomes deep | unchanged | Depth of field is never read back, although `FrameLayout.focus` exists |
| 2.3 | Key-light energy ×10 | Exposure and contrast change | unchanged | Energy is not diffed |
| 4.3 | World colour night → day | Time of day changes | unchanged | World colour is read but never compared |
| 3.3 | Lead walks 1 m sideways during the shot | Head exits frame right by the last frame (x 0.26 → 1.04) | unchanged | Objects are sampled only on the first frame |
| 2.2 | EDIT-timeline strip trimmed 96 → 72 frames | Shot is one second shorter in the cut | unchanged | VSE strips are written but never read |

The misses have three causes visible in the code. The first is *when* the bridge samples: `_key_frames` takes its sample frames from the camera's own F-curves. Motion that lives anywhere else — a parent rig, a Follow Path or Track To constraint, a driver, an NLA strip — is therefore invisible, and even keyed motion is checked only at its keys. Higgsfield's camera rules recommend "semantic parent rigs (orbit, dolly, handheld)", which is precisely the case that breaks ([blender_addon.py](/home/user/prompt-to-scene-creator/prompt2scene/blender/blender_addon.py), [HF skill: blender-lighting-camera](https://higgsfield.ai/plugins/blender)).

The second is *what the schema carries*: the `p2s-previs` format stores location, rotation and lens per key, and nothing about sensor size or fit, shift, clip range, depth of field or resolution. A large class of framing edits therefore has nowhere to go ([previs.py](/home/user/prompt-to-scene-creator/prompt2scene/blender/previs.py)).

The third is *what the diff compares*: `camera_changed` and `blocking_changed` check only part of what the bridge collects, so light energy, world colour and fog are read or backfilled but never compared, and subjects and set pieces are read once, at `frame_start` ([previs.py](/home/user/prompt-to-scene-creator/prompt2scene/blender/previs.py), [sync.py](/home/user/prompt-to-scene-creator/prompt2scene/blender/sync.py)). Walk-path read-back and the app-side refresh are already on the roadmap; the other gaps are not ([TODO.md](/home/user/prompt-to-scene-creator/TODO.md)).

### Identity and merge rules leak user work in three more ways

The latest commit treats Shift+D copies as additions. Whichever holder of a `p2s_id` sorts first alphabetically keeps it, on the theory that originals sort before their `.001` copies ([blender_addon.py](/home/user/prompt-to-scene-creator/prompt2scene/blender/blender_addon.py)). That holds until an artist names the copy. In the test, a duplicate of "calm silver sea · 5.3" was renamed "A barn (moved copy)" and moved 3 m. It took the original's id, and the untouched original was relabelled as a new piece ([local test](/tmp/claude-0/-home-user-Speaker-Diarization/e6d7b62f-0368-5f51-9db4-b4ef76e4f814/scratchpad/eval_bridge/identity.py)). This is the dependence on names that the research warns against: names are user-editable, auto-suffixed and capped at 63 bytes in 4.x, while `session_uid` resets on reopen (169 became 230) ([bpy 5.2.3](https://pypi.org/project/bpy/5.2.3/)).

User-added objects fare worse. Their ids are derived from their names, so renaming one on a later round trip reads as a delete plus an add; only parentless meshes count, so imported assets that arrive as an Empty with mesh children, or as collection instances, are ignored; and additions get an axis-aligned world box with yaw 0, which inflates any rotated piece ([blender_addon.py](/home/user/prompt-to-scene-creator/prompt2scene/blender/blender_addon.py)).

Re-running the build never updates a file in place. A plain re-run skips existing shot scenes and returns the existing EDIT scene unchanged, so shots added or retimed in the app never reach an existing .blend. Running it with `--force` builds a *second* scene per shot. In the test, a forced rebuild left **32 scenes**, and `collect_edits()` returned **30 entries for 15 shots**. The EDIT strips still pointed at the old scenes. The importer applied the artist's edit from one copy and flagged the stale copy as a spurious conflict; importing with `--force` would have reverted the edit ([local test](/tmp/claude-0/-home-user-Speaker-Diarization/e6d7b62f-0368-5f51-9db4-b4ef76e4f814/scratchpad/eval_bridge/force_edit.py)). Higgsfield's manifest rule is the opposite: ids persist as custom properties "so re-running the same manifest updates the managed datablocks instead of duplicating them" ([HF skill: blender-scene-spec](https://higgsfield.ai/plugins/blender)).

The merge model is whole-shot and one-directional. `shot_to_previs` reuses the Blender-authored previs only while the shot's fingerprint is unchanged. Any later in-app edit — a lens tweak, a duration change, a natural-language revision — silently rebuilds the previs from the 2D layout and the template move. In the test, an artist's three-key camera arc became the two-key dolly template after a 0.5 s duration change in the app, and the shot's previs source flipped from `blender` to `layout` ([local test](/tmp/claude-0/-home-user-Speaker-Diarization/e6d7b62f-0368-5f51-9db4-b4ef76e4f814/scratchpad/eval_bridge/app_edit_path.py), [previs.py](/home/user/prompt-to-scene-creator/prompt2scene/blender/previs.py)). Higgsfield's rules forbid exactly this: "changing it silently is forbidden" ([HF skill: blender-lighting-camera](https://higgsfield.ai/plugins/blender)).

The same test showed a smaller loss on import. `classify_move` compares only the first and last poses, so the 1 m arc registered as "camera position / framing adjusted" and the move label stayed `dolly_in`. That label is what the prompt writer hands to text-only camera models ([sync.py](/home/user/prompt-to-scene-creator/prompt2scene/blender/sync.py)).

All of these failures look like success, which is what makes them dangerous. A false positive costs a regeneration that the user sees and can cancel. A false negative tells the user the shot is unchanged, keeps the old take approved, and regenerates the old framing next time. A feature that promises "only the shots you changed" should bias its detector toward flagging. Every miss above comes from a gap in the schema or the sampling; none is a tolerance problem.

## Define a shot's state as what its camera sees

**Identity should be minted by the app and enforced by the extension, never inferred from names or sort order.** Every managed datablock carries `p2s_id` (a UUID), `p2s_kind`, `p2s_shot_id` and an export revision. That covers the scene, shot collection, camera object and data, light object and data, subject root, set piece, EDIT strip and marker. Values stay scalar, with any structure stored as JSON strings, because USD silently drops dict properties and FBX stringifies them ([bpy 5.2.3](https://pypi.org/project/bpy/5.2.3/)).

Store each object's exported name and transform alongside its id, as `p2s_src_name` and `p2s_src_matrix`. Ties are then broken by what an object was, not by what sorts first. A `depsgraph_update_post` or `save_pre` handler in the extension can spot a `p2s_id` held twice as soon as a duplicate appears and re-mint the newcomer. `collect_edits` should also write the ids it mints for user additions back into the file, so they survive renames ([bpy 5.2.3](https://pypi.org/project/bpy/5.2.3/)). User additions should include Empties with mesh children and collection instances, measured with oriented boxes.

Ids should also stop being positional on the app side; today they take the form `<shot>:subject:<index>`. Otherwise the field-level merge described below cannot match a subject after Claude re-orders a layout ([previs.py](/home/user/prompt-to-scene-creator/prompt2scene/blender/previs.py)). The popular open-source MCP for Blender server learned the same lesson. It now matches datablocks by a property stamped at import, after its name parser had mangled "nor_gl" into "gl" ([MCP for Blender addon.py](https://github.com/ahujasid/blender-mcp/blob/main/addon.py)).

**Change detection should hash a per-shot "view record" built from evaluated state on every frame.** Each frame records the camera's world matrix and its full intrinsics: focal length as the app's full-frame equivalent f36 = 18/tan(hfov/2), where hfov comes from lens, sensor size, sensor fit and render aspect, plus `shift_x/y` (measured in units of the larger frame dimension), clip range, focus distance, f-stop and resolution. Alongside the camera it records the world matrix, dimensions and armature bone matrices of every object inside the frustum, each light's type, colour, energy and direction, the world, and the shot's timing from both its scene range and its EDIT strip ([bpy 5.2.3](https://pypi.org/project/bpy/5.2.3/)).

Dense sampling is affordable. Evaluating every frame of all 15 demo shots (1,656 frames), with every object read, took **0.06 s** in `bpy` 5.2.3, about 0.04 ms per frame ([local test](/tmp/claude-0/-home-user-Speaker-Diarization/e6d7b62f-0368-5f51-9db4-b4ef76e4f814/scratchpad/eval_bridge/timing.py)). Heavier character rigs were not measured. Because the record reads evaluated results rather than authoring structure, it does not care whether motion comes from keys, a parent rig, a constraint, a driver or the NLA.

Quantise the record so float noise does not mark shots dirty; the research suggests about 1 mm and 0.05°. Comparing in image space would be better still, though this is an untested inference. Project subject joints and set-box corners through the camera and flag a shot when anything moves more than a few pixels at delivery resolution. A distant mountain jittering 3 cm then stays clean, while a 1 cm nudge to a macro close-up does not. Stamp the record's hash at export, recompute it on return, and store it on every take, so a stale take can be identified without guessing.

**Merging should be three-way and per field**, comparing the base (what was exported), the app (the shot as it is now) and Blender (what came back). Fields the artist changed in Blender become locked, so Claude's later replanning or a layout redraw cannot overwrite them. When the app changes a locked shot, apply the change as a delta on the Blender previs: a lens change rewrites the lens keys and keeps the path. If that is not possible, raise a field-level conflict. Never rebuild from the layout ([HF skill: blender-scene-spec](https://higgsfield.ai/plugins/blender)).

The build script should become an idempotent manifest applier. It finds datablocks by `p2s_id`, updates managed fields that are not locked, and adds or removes EDIT strips as shots come and go. Before any mutation it writes a labelled checkpoint: a scene snapshot, the protected objects, and "the planned created/modified/deleted names", following Higgsfield's checkpoint procedure ([HF skill: blender-scene-spec](https://higgsfield.ai/plugins/blender)). The shipped preview-then-apply flow already provides the dry run that Higgsfield performs before broad builds.

**Code should measure the geometry, but the model should choose the words.** The app's architecture makes "model-driven, never rule-driven" its first principle ([ARCHITECTURE.md](/home/user/prompt-to-scene-creator/docs/ARCHITECTURE.md)). The bridge's `classify_move` and `classify_angle` nonetheless write spec fields from fixed thresholds: 12° of yaw makes an orbit, and travel beyond 8% of the subject distance makes a dolly. They also collapse compound moves into one of 16 labels ([previs.py](/home/user/prompt-to-scene-creator/prompt2scene/blender/previs.py)).

A better split is for the bridge to emit the measured path, the re-projected layout and a few rendered previs frames. The revise model then re-describes shot size, move and lighting in the shot spec, with the classifier's label passed in only as a hint. Rendering the camera view and asking Claude to compare it with the pencil panel also closes the loop that SceneAssistant identifies as the weakness of open-loop scene builders. MCP for Blender's `look` tool provides the same check ([SceneAssistant](https://arxiv.org/pdf/2603.12238), [MCP for Blender README](https://github.com/ahujasid/blender-mcp/blob/main/README.md)).

Each detected change should map to the smallest action that makes the media true again. Today the bridge un-approves every changed shot, including one that was only trimmed, and takes do not record which shot revision produced them ([sync.py](/home/user/prompt-to-scene-creator/prompt2scene/blender/sync.py), [schemas.py](/home/user/prompt-to-scene-creator/prompt2scene/schemas.py)). The research's classification, extended with Higgsfield's asset-swap rule ([HF skill: blender-lighting-camera](https://higgsfield.ai/plugins/blender)), gives this table:

| Change class (from the view record) | Smallest correct action | Shipped bridge today |
|---|---|---|
| Timing only, within the existing clip | Re-trim or re-time; keep approval and take | Un-approves the shot |
| Timing only, beyond the clip | Regenerate or extend; check target durations | Un-approves; duration later snapped to the target without warning |
| Camera only | New keyframe and clip; reuse identity references | Un-approves; layout re-projected |
| Blocking or pose | New keyframe and clip | First-frame positions only |
| Lights or atmosphere only | Restyle the keyframe, then the clip | Energy, world and fog ignored |
| Shared set element | Every shot whose frustum contains it | Sets are per-shot copies |
| Hero asset swap | Re-check every camera set against the old shell | Not handled |

Content-address every generated artifact by a hash of its conditioning inputs, prompt, model, parameters and seed. Mark superseded takes stale instead of deleting them, and submit jobs with idempotency keys. Higgsfield reuses an idempotency key after an uncertain timeout rather than resubmitting ([HF skill: blender-generation](https://higgsfield.ai/plugins/blender)).

Every Blender edit is also the most specific supervision the app's learner will ever receive, because it records exactly where a human moved Claude's framing. The architecture already treats every take as a training signal ([ARCHITECTURE.md](/home/user/prompt-to-scene-creator/docs/ARCHITECTURE.md)). Edits deserve the same treatment, logged as labelled preference pairs of the layout Claude planned against the layout the artist made.

## One scene per shot is right, and the cut must talk back

Studios structure previs in Blender in two ways. The first is one continuous-action scene covered by many cameras, where each shot is a camera plus a frame range bound through timeline markers. This is the SPA Sequencer and Ubisoft Shot Manager model, in which "a take is an edit" ([SPA Sequencer](https://extensions.blender.org/add-ons/spa-sequencer/), [Shot Manager philosophy](https://github.com/ubisoft/shotmanager/blob/main/docs/getting-started/general-philosophy.rst)). The second gives each shot its own scene or file, with assets linked in. Storypencil's scene strips work this way, as do shot files built by Kitsu ([Storypencil manual](https://www.blender.org/manual/en/addons/sequencer/storypencil.html), [Blender Artists](https://blenderartists.org/t/file-organization-for-animated-short-film/1190776)).

Blender has no native shot entity. Shot Manager advertises "a true shot entity", and a community add-on thread is titled "Blender has no native concept of shot states" ([Shot Manager README](https://github.com/ubisoft/shotmanager), [Hyper Shot](https://blenderartists.org/t/hyper-shot-blender-has-no-native-concept-of-shot-states-so-i-built-one/1641870)). The app should keep owning that entity in its schema and mirror it into markers and the VSE rather than depend on an add-on. Shot Manager has been unmaintained since version 2.1.46 in February 2023 and is incompatible with native camera binding. Higgsfield's add-on, meanwhile, already requires Blender 5.1+ ([Shot Manager CHANGELOG](https://github.com/ubisoft/shotmanager/blob/main/CHANGELOG.md), [Shot Manager features](https://github.com/ubisoft/shotmanager/blob/main/docs/main-panel/features.rst), [Higgsfield help center](https://higgsfield.ai/creator-hub/help-center/integrations/external-integrations-higgsfield)).

Per-shot scenes are the right default, because Claude plans each shot as its own tableau and only changed shots may regenerate. A continuous-action mode is still worth offering for coverage, such as a dialogue scene shot from four angles. There, one blocking edit should dirty every shot whose camera sees it, and the view record handles that without special cases.

Per-shot scenes need shared sets, which the bridge does not have yet. Every shot gets its own copy of every proxy, so moving the lighthouse means moving it once per shot ([blender_addon.py](/home/user/prompt-to-scene-creator/prompt2scene/blender/blender_addon.py)). The research pattern is a base set per app scene, linked or instanced into each shot scene, as with Storypencil's "base scene". Dirtiness is then decided per camera frustum, so only the shots that actually see a moved piece update ([Storypencil manual](https://www.blender.org/manual/en/addons/sequencer/storypencil.html)).

The proxy conventions worth adopting come from Higgsfield and MCP for Blender: role-coloured semantic proxies (hero, support, background, occluder) at real metre scale with the origin at the feet, a rig-ready A- or T-pose, and Mixamo-style bone names so that generated motion retargets onto the mannequins; Higgsfield imports such motion as a 27-bone armature at the clip's 20 fps ([HF skill: blender-greybox](https://higgsfield.ai/plugins/blender), [MCP for Blender README](https://github.com/ahujasid/blender-mcp/blob/main/README.md)). Cameras should sit on semantic parent rigs (dolly, orbit, crane, handheld) so the move type stays legible, with one primary move per 2–30 s clip ([HF skill: blender-greybox](https://higgsfield.ai/plugins/blender)). These are exactly the rigs the current detector cannot see. Dense evaluated sampling is therefore a prerequisite for the recommended workflow, not a refinement.

**The EDIT scene is where editors naturally work, so it must be an input as well as an output.** The bridge stamps `p2s_shot_id` on every strip and then never reads one back ([blender_addon.py](/home/user/prompt-to-scene-creator/prompt2scene/blender/blender_addon.py)). The return path should read each strip's handles, channel and order, any CROSS overlaps, and the marker frames, and map them to duration, shot order and `transition_in`. The handles are `left_handle`, `right_handle` and `duration` in 5.1+. On 4.5 use `frame_final_*`, which 5.2 deprecates for removal in 6.0. A trim inside the existing clip then becomes a re-trim rather than a regeneration ([bpy 5.2.3](https://pypi.org/project/bpy/5.2.3/), [fake-bpy-module-5.1](https://pypi.org/project/fake-bpy-module-5.1/)). A cross dissolve needs its clips to overlap by its length, because butted clips produce a zero-length effect.

Frame rate needs explicit handling. The RNA `strips.new_movie()` neither retimes a clip nor changes the scene fps, so a 23.976 fps clip lands 1:1 in a 24 fps cut and drifts. On the way back, the bridge rounds `fps / fps_base` to an integer, so a 23.976 scene reads as 24 ([bpy 5.2.3](https://pypi.org/project/bpy/5.2.3/), [blender_addon.py](/home/user/prompt-to-scene-creator/prompt2scene/blender/blender_addon.py)). Store `fps` and `fps_base` in the manifest, and conform clips explicitly.

For interchange beyond Blender, **OpenTimelineIO is the standard format**. `opentimelineio` 0.18.1 (Apache-2.0, with cp313 wheels) has separate adapters for CMX 3600 EDL, FCP7 XML, FCPXML, AAF, ALE and Kdenlive, so one OTIO export from the app reaches every mainstream NLE ([opentimelineio 0.18.1](https://pypi.org/project/opentimelineio/0.18.1/), [otio-cmx3600-adapter](https://pypi.org/project/otio-cmx3600-adapter/), [otio-aaf-adapter](https://pypi.org/project/otio-aaf-adapter/), [otio-fcpx-xml-adapter](https://pypi.org/project/otio-fcpx-xml-adapter/)). There is no Blender OTIO adapter on PyPI, and Blender's core add-ons include no EDL, OTIO or FCPXML importer. The bridge must therefore map OTIO to the VSE itself, which is what OTIO's tool list says Shot Manager and a "Blender VSE IO" add-on do ([OTIO wiki](https://github.com/PixarAnimationStudios/OpenTimelineIO/wiki/Tools-and-Projects-Using-OpenTimelineIO)). Clip names should equal shot ids, and the mapping is mechanical:

| OTIO | Blender VSE |
|---|---|
| Track | Channel |
| Clip with `ExternalReference` (name = shot id) | `strips.new_movie`, trimmed from `source_range` through `content_trim_start` or `left_handle_offset` |
| Gap | Frame offset |
| Transition (SMPTE_Dissolve) | CROSS effect over an overlap |
| Marker | `timeline_markers` |
| `RationalTime(rate)` | `render.fps` / `fps_base` |

Media and storyboard panels need four rules. **Video cannot be packed into a .blend** (neither `MovieStrip` nor `MovieClip` has a packed file), so clips ship in `media/` beside it, with absolute paths passed into `bpy` and the file saved with `relative_remap=True` ([bpy 5.2.3](https://pypi.org/project/bpy/5.2.3/)). **Storyboard panels must be rasterized**: the app's panels are SVG ([ARCHITECTURE.md](/home/user/prompt-to-scene-creator/docs/ARCHITECTURE.md)), Blender loads an SVG as a silent 0×0 image, and AVIF loaded in 5.2 but failed just as silently in 4.2, so the server should convert boards to PNG or WebP and check `img.size` after every load ([bpy 5.2.3](https://pypi.org/project/bpy/5.2.3/), [bpy 4.2.23](https://pypi.org/project/bpy/4.2.23/)). **The pencil panel belongs in the camera.** The bridge's only camera background today is the latest generated keyframe, whereas the research recommends the panel itself, after Shot Manager's camera backgrounds, so the artist blocks against Claude's plan with the keyframe as a second background image ([Shot Manager features](https://github.com/ubisoft/shotmanager/blob/main/docs/main-panel/features.rst)). Finally, **set `frame_method` explicitly**, because it defaults to FIT in 5.2 and STRETCH in 4.2 ([bpy 4.2.23](https://pypi.org/project/bpy/4.2.23/)).

Transport should stay file-first, through JSON exported from the panel or a .blend uploaded for a headless read. That path already works offline and needs no live socket ([BLENDER.md](/home/user/prompt-to-scene-creator/docs/BLENDER.md)). The live "Apply changes to app" button posts unauthenticated JSON to `P2S_PUBLIC_URL`. That is fine on localhost, but the hosted deployment the architecture describes sits behind an authenticating gateway. The bundle should therefore carry a short-lived, project-scoped import token, and the extension should declare its network permission ([blender_addon.py](/home/user/prompt-to-scene-creator/prompt2scene/blender/blender_addon.py), [ARCHITECTURE.md](/home/user/prompt-to-scene-creator/docs/ARCHITECTURE.md)).

MCP for Blender shows the risk of a live channel done carelessly: its remote mode "has no authentication or encryption and lets clients run Python in Blender" ([MCP for Blender README](https://github.com/ahujasid/blender-mcp/blob/main/README.md)). Higgsfield's connector shows that an agent-driven live loop works. It is a convenience layer over the file round trip, not a replacement for it ([Higgsfield help center](https://higgsfield.ai/creator-hub/help-center/integrations/external-integrations-higgsfield)).

## Hosted video models take references, not geometry

**Dense per-frame structural control from Blender passes is documented only for open models.** The LTX-2 IC-LoRA adapters take depth, pose or canny sequences and list Blender as a depth source ([LTX docs: IC-LoRA](https://docs.ltx.video/open-source-model/usage-guides/ic-lo-ra)). Wan VACE 2.1 and 2.2 take depth and pose control videos, usually through ComfyUI ([RunComfy: Wan 2.2 VACE](https://www.runcomfy.com/comfyui-workflows/wan-2-2-vace-in-comfyui-pose-driven-motion-video-workflow?action=run-workflow)). An existing "Blender to ComfyUI AI Renderer" workflow already drives Wan VACE from Blender depth, outline and pose passes ([RunComfy: Blender to ComfyUI](https://www.runcomfy.com/comfyui-workflows/blender-to-comfyui-ai-renderer-2-0-workflow-cinematic-video-output)).

Hosted models take weaker signals. Third-party guides say **Seedance 2.0** accepts up to nine reference images and three reference videos (about 15 s combined), with roles assigned by @-tags. One user report says a circling push-in reference clip was reproduced ([WaveSpeed guide](https://wavespeed.ai/blog/posts/seedance-2-0-complete-guide-multimodal-video-creation/), [Technology.org](https://www.technology.org/2026/02/23/how-i-used-reference-videos-to-replicate-complex-camera-movements-in-seedance-2-0/)). **Veo 3.1** takes first and last frames plus up to three reference images, though sources report its request schema inconsistently ([Google AI forum](https://discuss.ai.google.dev/t/how-does-veo3-1-achieve-the-using-first-and-last-frames-function-through-the-api/112947)). **Kling 3.0 Motion Control** takes an appearance image, an Element and a motion video of at most 10 s (30 s when the character's orientation follows the video rather than the image); it has no camera parameter, so camera intent goes in the prompt, and gateway notes ask for reference videos with "clear human motion without cuts or camera movement" ([Kling API: Motion Control](https://kling.ai/document-api/api/video/motion-control), [Evolink: Kling 3.0 Motion Control](https://evolink.ai/kling-v3-motion-control)). Runway Aleph restyles existing footage ([Layer: Gen-4 Aleph](https://www.layer.ai/docs/models/runway-gen4-aleph)).

No documentation found shows a hosted model accepting 3D, depth or a camera path as geometry rather than as a style reference. Seedance 2.0's own technical report rates advanced camera movement as the hardest category, with no model above 3.14 on any metric. That comes from a snippet; the paper itself could not be opened ([Seedance 2.0 report](https://arxiv.org/pdf/2604.14148)).

**The recipe that keeps output photographic is structure from 3D, look from references, keyframe first.** From each edited shot camera, render conditioning at the first frame, and at the last frame where the target supports it: depth, line art or canny, an OpenPose skeleton projected from the mannequin's joints, per-subject masks, and a clay view. Turn that frame into a photoreal keyframe with a composition-preserving image model, either a depth- or line-controlled model as in NVIDIA's Blender-depth-to-photoreal-image graph, or an editing model given the clay render with a strict keep-composition instruction, which is Higgsfield's `gpt_image_2` restyle route ([NVIDIA RTX guide](https://www.nvidia.com/en-us/geforce/news/rtx-ai-video-generation-guide/), [HF skill: blender-volatile](https://higgsfield.ai/plugins/blender)). Identity comes from the character sheets, never from the grey proxies. Only then animate the keyframe, adding motion signals where the camera move matters. Higgsfield's per-shot deliverable is the right artifact to standardise on: an H.264 MP4 plus its exact first-frame PNG at 1280×720, for a 2–30 s clip checked at its start, middle and end frames ([HF skill: blender-greybox](https://higgsfield.ai/plugins/blender)). Durations in the table come from the app's own target profiles ([targets.py](/home/user/prompt-to-scene-creator/prompt2scene/targets.py)):

| Target | Best Blender-derived input (documented) | Photoreal tactic | App duration profile | Still unverified |
|---|---|---|---|---|
| Seedance 2.0 | Photoreal keyframe and identity images as `@Image`; greybox or depth MP4 as `@Video1` | Prompt states the video is "camera movement and blocking only" | 4–15 s, up to 9 images | Official API field names; whether a depth video is read as geometry or style |
| Veo 3.1 | Restyled first and last frames; up to 3 references | Camera move written precisely in text | 4, 6 or 8 s | Exact request schema; references on Veo 3.1 Fast |
| Kling 3.0 | Image-to-video from the keyframe; for performance, Motion Control with a mannequin rendered from a locked-off camera | Photoreal appearance image; camera in the prompt | 5 or 10 s; motion reference ≤10 s or ≤30 s | Start/end-frame and camera options on 3.0 |
| Wan 2.2 | VACE depth control video plus a first-frame reference | Moderate or decaying control strength | 2–5 s | Whether the hosted provider exposes VACE |
| Sora 2 | Not researched | Treat as keyframe plus text camera until verified | 4, 8 or 12 s | Inputs and camera control |
| LTX-2 (optional) | IC-LoRA depth, pose or canny | About 0.6 depth strength; style-only prompts | — | — |
| Runway Aleph (optional) | Video-to-video restyle of the clay MP4 plus 3 references | Photoreal references | — | Structure fidelity and limits |

Guardrails keep the grey out of the pixels. **Never pass a clay or greybox render as an appearance or style reference**: Invideo's guidance is blunt that "a grey render is not automatically a technical depth pass" and should be labelled a camera or composition reference unless a real depth map was exported ([Invideo FAQ](https://invideo.io/faq/how-do-you-use-a-blender-blocking-render-as-a-camera/)). **Label every reference's role**, since guides warn that unnamed Seedance references "may be ignored or misinterpreted" ([WaveSpeed guide](https://wavespeed.ai/blog/posts/seedance-2-0-complete-guide-multimodal-video-creation/)); the app's `VisualPrompt.references` is an untyped list of URLs, so previs-derived inputs need a role field before they enter it ([schemas.py](/home/user/prompt-to-scene-creator/prompt2scene/schemas.py)). Prefer depth to pose for small or occluded figures, because depth is reported to be the more stable control ([ComfyUI.org: Wan depth control](https://www.comfyui.org/en/unlock-advanced-video-depth-control-wan-model)), and keep control strength moderate: about 0.6 is one LTX guide's starting point for approximate structure, and VACE strength can decay over the clip so later frames gain realistic detail, though both values are anecdotal ([LTX blog](https://ltx.io/model/model-blog/how-to-use-ic-lora-in-ltx-2), [ComfyUI-WanVaceAdvanced](https://www.runcomfy.com/comfyui-nodes/ComfyUI-WanVaceAdvanced)). Match aspect ratio and fps between Blender and the model ([RunComfy: Blender to ComfyUI](https://www.runcomfy.com/comfyui-workflows/blender-to-comfyui-ai-renderer-2-0-workflow-cinematic-video-output)), write prompts about look and light rather than motion when motion comes from a control video ([LTX docs: IC-LoRA](https://docs.ltx.video/open-source-model/usage-guides/ic-lo-ra)), and keep the keyframe's light direction consistent with the Blender key light by writing the light's camera-relative azimuth into the prompt.

Three app-specific traps follow. First, community depth adapters condition on monocular-estimator depth video ([Hugging Face: LTX-2.3 depth IC-LoRA](https://huggingface.co/SyFeee/ltx2.3-chinese-drama-iclora-depth)). Running an estimator on the clean clay render is therefore a cheap way to match that distribution; raw Blender Z, normalised per shot, is the alternative. Neither was compared in this research. Second, the bridge draws surreal elements as violet, emissive proxies ([BLENDER.md](/home/user/prompt-to-scene-creator/docs/BLENDER.md)), exactly the CG look that must stay out of appearance references. Photographic-surreal shots should get their impossible element inside the photoreal keyframe, placed by a previs mask and described in text, so the video model animates a photographed impossibility rather than a glowing box. Third, the app's judge already scores photorealism as its own dimension ([ARCHITECTURE.md](/home/user/prompt-to-scene-creator/docs/ARCHITECTURE.md)). That score is the natural gate for tuning control strength per target.

For targets that take the camera only as text — Veo and Kling, and Sora until verified otherwise — the previs's precision survives only if the measured path is put into words. The shot spec's single move label, lens and angle cannot carry an arc, an ease-in, or a push-in that ends on a profile, and in the arc test above the label did not change at all. The prompt writer should receive a camera-path summary from the view record — travel in metres relative to the subject, pan and tilt in degrees, the lens change, the speed profile, and the start and end framing of the lead — alongside the label. Shots with more than one primary move should be split rather than trusted to a compound prompt. That follows Higgsfield's one-primary-move rule and the Seedance report's finding that advanced moves are the hardest ([HF skill: blender-greybox](https://higgsfield.ai/plugins/blender), [Seedance 2.0 report](https://arxiv.org/pdf/2604.14148)). Durations need a check at import. The app snaps each shot to the target's allowed lengths without telling the user, so a Blender retime to 7 s becomes 8 s on Veo and 5 s on Kling ([targets.py](/home/user/prompt-to-scene-creator/prompt2scene/targets.py)). The import report should warn while the artist is still in Blender.

Rendering those passes in Blender 5.x has traps that Higgsfield's version notes document. The compositor tree moved from `Scene.node_tree` to `Scene.compositing_node_group` and `CompositorNodeComposite` no longer exists; a compositing group without a Render Layers node makes Blender skip rendering and write a transparent black frame ("a suspiciously fast render is this bug"); Blender 5.1 background sessions can omit FFMPEG as an output format; and the EEVEE engine enum differs between scenes ([HF skill: blender-volatile](https://higgsfield.ai/plugins/blender)). Headless rendering from the PyPI wheel was not tested in this research.

Keep a per-frame camera-path JSON of intrinsics and extrinsics with every shot. Research from 2025–2026 converges on rendering an explicit 3D proxy along the target camera and conditioning video on those renders. Examples are GEN3C's 3D cache, 3DScenePrompt's point-cloud memory (ICLR 2026), E³C's rendered skeletons, Track2View's projected point tracks, and LiVER's editable layout, lighting and camera proxy ([GEN3C](https://research.nvidia.com/labs/toronto-ai/GEN3C/), [3DScenePrompt](https://cvlab-kaist.github.io/3DScenePrompt/), [E³C](https://arxiv.org/pdf/2605.26316), [Track2View](https://arxiv.org/html/2606.15534), [LiVER](https://arxiv.org/html/2604.07966)). The papers were read only through search snippets. An edited Blender previs is already such a proxy, so the artifacts that drive Wan VACE today will also suit any hosted camera-conditioned endpoint that appears.

## Twelve fixes ranked by the user work they protect

The bridge needs no architectural rewrite. Its gaps are concentrated in what it samples, what it compares and how it merges. The fixes are ranked below by how much silently lost work each one prevents.

| Rank | Change | What it closes |
|---|---|---|
| 1 | Sample the evaluated camera on every frame; extend the schema to sensor size and fit (f36 from hfov), shift, clip, depth of field and resolution | Parent-rig dolly, easing, sensor-fit, shift and DoF misses |
| 2 | Sample every frustum-visible object per frame, including armature pose; diff light energy and type, world and fog | Animated blocking, light and world misses |
| 3 | Read the EDIT timeline: strip handles, order, channel, transitions, markers | Ignored trims and reorders |
| 4 | Make the build an idempotent manifest applier that updates by `p2s_id`, refreshes EDIT strips and checkpoints first; retire the parallel-scene `--force` | Duplicated scenes, stale cuts |
| 5 | Field-level three-way merge with Blender-locked fields; stop `shot_to_previs` from rebuilding a Blender previs after an app edit | Reverted camera arcs |
| 6 | Extension-enforced UUIDs: re-mint duplicates in a handler, write ids for additions back, tie-break by stamped name and transform, capture hierarchies and instances with oriented boxes | Renamed-duplicate id theft, rename churn |
| 7 | Change classes mapped to the smallest regeneration; takes store the view-record hash; trims keep approval | Needless regeneration, unidentifiable stale takes |
| 8 | Ship as an Extension with network and files permissions; floor at 4.5 LTS; CI on the 4.5.15 and 5.2.3 wheels; scoped import tokens | Invisible panel, unauthenticated hosted imports |
| 9 | Import-time checks against target durations and the one-primary-move rule | Silent duration snapping, compound moves |
| 10 | Per dirty shot: structure passes, clay MP4 plus first-frame PNG, camera-path JSON; role-typed references; keyframe-first recipes per target | Grey-look leakage, weak camera adherence |
| 11 | OTIO export and import of the cut; rasterized panels as camera backgrounds; explicit fps conformance | NLE hand-off, 23.976 drift, SVG boards |
| 12 | Linked base sets per app scene; an optional continuous-action mode with frustum-based dirtiness; a USD export parsed server-side with `usd-core` | Per-shot set copies, DCC hand-off |

The first five are correctness fixes, and they should land before any generation work builds on the previs. All five can be regression-tested with the harness used for this report: build the project, apply one edit per shot, collect, and require an "updated" verdict for every row of the edit table above. Today only the positive control passes.

## Conclusion

The deeper lesson of the experiments is that the round trip's unit of truth is the camera's view, not the object list. A single evaluated sampling pass that records, frame by frame, what each shot camera sees can do three jobs at once. Its hash decides which shots are dirty, its projections keep the storyboard panel in step with the 3D, and its passes and camera path condition the video models. Built that way, the bridge stops depending on how an artist constructs a move (keys, rigs, constraints, drivers) and on how they name or duplicate objects, which is where every failure observed here came from. "Only the shots you changed" then stops being a promise about bookkeeping and becomes a measurable property: a shot regenerates exactly when its camera sees something different.

On the generation side, no hosted model found accepts geometry. The previs's precision therefore reaches Seedance, Veo and Kling through only three channels: the photoreal keyframe carries composition, the prompt carries the camera path, and for Seedance a role-labelled reference video carries motion. A measured camera-path summary and first-and-last-frame keyframes are worth more engineering than any additional render pass. For shots where the camera move itself is the point, the only documented way to make the camera follow the edited path is dense control on an open model, Wan VACE or LTX-2. That argues for bringing the roadmap's self-hosted Wan 2.2 workers forward as a lane for camera-critical shots, rather than leaving them as an investment in training alone ([TODO.md](/home/user/prompt-to-scene-creator/TODO.md)).
